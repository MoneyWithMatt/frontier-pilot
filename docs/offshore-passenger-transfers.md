# Offshore passenger transfers — operation and acceptance

Authority: [approved specification](specs/offshore-passenger-transfers.md). Track [task #2](https://github.com/MoneyWithMatt/frontier-pilot/issues/2), [draft PR #3](https://github.com/MoneyWithMatt/frontier-pilot/pull/3) and [handoff](handoffs/offshore-career.md).

## Implemented airport loop

Skeleton Coast Petroleum retains its FYWB base and $800 per verified airborne hour. Passenger transfers is a separate page: reserve one specialist, select an eligible Vision Jet, qualify at origin, explicitly board, fly, qualify arrival, explicitly disembark, view the completed transfer/wage. One passenger/seat is a labelled prototype fixture, not a certification of real seat capacity. Boarding is simulated; no MSFS seats, payload, animation or NPCs are manipulated. The cargo system remains real cargo and retains its existing physical loading path.

Both endpoint aircraft restrictions are required at generation/reservation/boarding. Exact TITLE/model mappings and selected individual-airframe guards are shared with cargo dispatch. One boarded passenger flight excludes loaded cargo and other passenger boarding. Pending cargo intents must be reconciled first. Cargo positive application, boarded authorization and restoration consult the passenger guard before native writes; domain validation also rejects mixed loads.

Offers use the existing persisted UTC cadence/lifetime, one per selected route per cadence with the existing slot cap. Accepted/boarded transfers survive expiry. Disconnect/invalid/stale/nonadvancing telemetry, identity mismatch and excessive discontinuity pause transient qualification without deleting the passenger or durable flight facts. Airborne wages use the same helper as cargo; ground, gaps and restart time are excluded. The existing tracker distance/radius/continuous-stop policies are reused without adding a new pause/slew or anti-teleport policy.

Passenger records are stored in schema-11 `economy-state.json`; flight progress is embedded. Atomic completion records terminal flight state, the passenger delivery, one PilotWage ledger entry and the balance together. The existing ledger remains money authority. Completion retries and later telemetry cannot pay twice. Native passenger/payload state is not claimed recoverable because it is not written.

## Platform integration boundary

`PassengerEndpoint` distinguishes Airport and Platform. `CanGenerate` permits only Airport. A Platform endpoint is rejected by mission validation even if it has plausible coordinates, and no platforms are authored or registered. There is deliberately no editable "qualified" checkbox. This prepares the endpoint contract without routing a platform through the broad airport arrival radius.

The [SDK assessment](offshore-career.md#official-sdk-capability-assessment) identifies facility-detail geometry, elevated-surface variables and relative-motion limitations. Existing `IAircraftOperationalAdapter`/fleet platform-height contracts provide additional qualification boundaries, not an enabled platform adapter. Successful live evidence, an accepted exact platform/aircraft record, deck-specific completion rules and a reviewed adapter/registry change are all prerequisites to enabling platforms. Passing the airport tests or finding an identifier is insufficient.

## Platform live qualification — prerequisite for future activation

This is a read-only qualification proposal, not permission to launch a changed executable, create/install scenery, issue payload/position commands or enable a destination.

1. Approve one **existing static platform**, one exact candidate aircraft and the observer artifact. Record provenance, identifier/object identity, WGS84 deck centre, dimensions/bounds, deck elevation/datum and version hashes. No guessed petroleum platform or inference from a generic airport reference point.
2. Validate the native detail reader's packet framing/completeness and correlate facility data with the actual visible/collidable deck. Record location/altitude/contact/surface values on dry airport ground, on deck, over nearby water, alongside/below deck and over a neighbouring surface. Use aircraft data only; camera/avatar/last-known values cannot qualify aircraft arrival.
3. Distinguish touchdown from low hover. Surface-relative zero speed alone is insufficient; SDK documentation also describes it for hovering over moving vessels. Demonstrate stable horizontal and vertical deck containment, actual contact and time/identity continuity. Record any datum offsets instead of tuning them by guess. Moving vessels remain outside this static-platform slice.
4. Test disconnect, reconnect, application restart, aircraft change, scene loading, pause/slew signals and nearby invalid surfaces without producing passenger delivery evidence. Demonstrate retained qualified identity/geometry after restart and failure when environment/aircraft versions change. Repeat on the exact final candidate artifact.
5. If native passenger/payload integration is later proposed, separately qualify that aircraft's station/seat mapping, weight retention, boarding transitions and readback/recovery before writes become authoritative. Simulated airport boarding does not confer this capability.
6. Publish a redacted evidence record with exact versions, inputs, timestamps, expected/observed results and rejected cases. Matt must accept the live result. Only then implement/review the platform qualification registry/adapter and deck-specific mission rules, plus negative tests proving missing/stale/mismatched qualification blocks generation. Keep the shipped Platform gate closed until those prerequisites pass.
